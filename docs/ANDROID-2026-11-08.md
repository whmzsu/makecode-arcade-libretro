## 结论先说（2026-11-08 13:28 定稿，14:30 补常规长测机）

1. **Android 可用，0.3.5 无需任何改动**：两台机器在 RetroArch 里都实测通过 ——
   Motorola XT2301-5（8 Gen 2 / Android 16）上 0.2.7 / 0.3.5 / 两个 0.3.5 对照构建
   （035b、035c）**全部能加载并跑游戏**；罗技 G Cloud（Android 11）上 0.3.5 加载正常、
   8 张卡带全部正常。
2. **自动化测试可行**：`tools/mca_host_android.c` 编成 arm64 可执行文件推到
   `/data/local/tmp` 就能 dlopen 核心、跑任意帧数、算末帧 MD5（与 `libretro_host.py`
   同口径）。桌面版跑 x86_64 核心得到 `f93e4597…` / `23210fb3…`，与既有基线逐位一致。
3. **但 SDK ≥ 30 的 shell 宿主里必然 `PANIC 906`**，原因是 bionic 给非 app 进程的堆指针

4. 一路上出现过的"0.3.5 加载不了核心 / 列表底部没有 core 信息"，复核后是**测试操作失误**

   `core_info.cache` 解出来含 3 条 MakeCode 条目（0.3.5 / 035b / 035c），名字、扩展名、
   备注全部正确。

## 更正：真凶是「进程的堆指针打标（TBI）」，不是核心

| 进程 | `targetSdkVersion` | malloc 返回值 | pxt 能否工作 |
|---|---|---|---|
| `adb shell` 启动的可执行文件（`mca_host`） | 10000（非 app） | `0xb400_0072_e9e18b00`（top byte = `0xb4`） | ✗ 高 16 位非 0 → 被判成 double |
| RetroArch `com.retroarch.aarch64` | **28**（实测 1.21 / 1.22 都是 28） | `0x7f…` / `0x7…`（top byte = 0） | ✓ |
| 任意 `targetSdk>=30` 的 app | ≥30 | 同上打标 | ✗ |

- Android 11 起 bionic 对 `targetSdkVersion >= 30` 的进程开启 **堆指针打标（TBI，
  top-byte-ignore）**，malloc 返回的指针高字节是随机 tag（实测恒为 `0xb4`）。
  `pxtbase.h` 的 `isDouble(v) = (v >> 48) != 0` 会把这些指针全判成数字 → `PANIC 906`。
- 实测无法从进程内关掉：`android_mallopt(M_BIONIC_SET_HEAP_TAGGING_LEVEL, NONE)`
  对非 app 进程返回 `false`（`rc=0`），之后 `malloc` 仍然带 tag。
  正确 opcode 是 `-204`（NDK `malloc.h` 的 `M_BIONIC_SET_HEAP_TAGGING_LEVEL`），
  别用网上的 13。
- 两台真机实测（G Cloud Android 11 / Moto XT2301-5 Android 16）在 shell 宿主下
  **都是 `0xb400…`、都 `PANIC 906`**；而用户在 Moto 上用 RA **确实跑通过 jumpy** ——
  差别只在宿主进程的 targetSdk，与 OS 版本、SoC、核心版本都无关。
- 结论：**RetroArch 前端下 Android 可用，不需要移植**；需要移植的场景只有"自己的
  APK（targetSdk≥30）里加载本核心"。若以后要做，就按下面那节的低地址方案走。

## 怎么跑（白盒）

```bash
NDK=".../android-ndk-r27c/toolchains/llvm/prebuilt/windows-x86_64/bin"
"$NDK/clang.exe" --target=aarch64-linux-android21 -O2 -Itools -Icore \
    tools/mca_host_android.c -o out/android/mca_host
adb push out/android/mca_host core.so /data/local/tmp/mca/
adb shell 'cd /data/local/tmp/mca && chmod 755 mca_host && \
           ./mca_host ./core.so ./ping.pxt64 120 --data-dir=/data/local/tmp/mca/data'
```

输出锚点与 py 宿主一致：`FINAL-FRAME-HASH <md5>  (160x120, 独立帧 N)` + `STATS …` + `HOST-OK`。

> 坑（14:05 修）：Android 上 `read_file()` 把卡带镜像 `mmap` 到 `0x600000000`（低地址，避开
> NaN-boxing），但收尾时曾无条件 `free(data)` —— 对 mmap 指针调 `free` 会让 jemalloc 在
> `huge_salloc` 里 SIGSEGV（崩溃时 `x0` 正好等于那个 mmap 基址）。现在统一走 `release_cart()`
> （Android → `munmap`，其他平台 → `free`），退出码恢复为 0。这个 bug 与核心无关，只影响宿主。

## 一键回归（测试 APK，不用碰屏幕）

SDK ≥ 30 的设备上 `mca_host` 跑在 shell 域必然撞 TBI（见下节），那种设备只能改用
**无头测试 APK**；SDK < 30 则直接用 `run_shellhost.sh`，不必装 APK（见文末「常规长测机」）：
`tools/android_test/`，一个没有 Java 代码的 NativeActivity，`targetSdkVersion=28`（与
RetroArch 一致，从而避开堆指针打标）。

```bash
# 1) 打 APK（核心会被拷进 APK 的 lib/<abi>/libmca_core.so，换核心就重打，几秒钟）
bash tools/android_test/build_apk.sh                     # 默认 arm64-v8a + core/dist/aarch64-linux-android21

# 2) 一键跑一批卡带，并与桌面基线逐张比哈希
bash tools/android_test/run_on_device.sh \
     --carts out/deploy/stage --frames 600 \
     --baseline out/android_test/baseline.txt --install
```

机制要点：
- 每张卡带**单独起一次进程**（`am force-stop` → `am start`），一张崩了不影响下一张，
  与 `mca_host` 的进程隔离语义等价；
- 结果行格式 `RESULT <卡带> <末帧md5> frames=N WxH distinct=D audio=A/P` 同时写 logcat
  （tag `MCA-TEST`）和 `<外部数据目录>/results.txt`，逐行 flush，崩了也不丢前面的；
- 桌面基线用同一份 MD5 实现（`tools/mca_md5.h`，与 `mca_host_android.c` 共用），
  基线文件格式就是同样的 `RESULT` 行，`--baseline` 直接 diff；
- 输入藏在 `/sdcard/Android/data/org.mca.coretest/files/`：`carts/*.pxt64`、`frames.txt`、
  `only.txt`（只跑其中一张）。

已验证（离线）：APK 结构 targetSdk=28、`lib/arm64-v8a/{libmain.so,libmca_core.so}`、
`libmain.so` 只依赖 `libandroid/liblog/libdl/libc`、导出 `ANativeActivity_onCreate` 与
`android_main`；MD5 实现用 `abc` / 空串 / 38400 字节三组向量对齐系统 `md5sum`。

注意事项：
- Git Bash 里 `adb push` 的远端路径会被 MSYS 改写 → 必须 `export MSYS_NO_PATHCONV=1`。
- `adb push` 覆盖已存在文件会掉执行位 → 覆盖后要再 `chmod 755`。
- 宿主**刻意不 dlclose**：核心里有 static 析构，卸载后进程退出时 atexit 链会跳进已解除
  映射的代码段（SIGSEGV in `__run_exit_handlers`）。真机 RetroArch 退出的 139 是同一类。
- 设备 `/data/local/tmp` 可执行（shell 域），不需要 root。

## 为什么 SDK ≥ 30 时 shell 宿主里跑不了（PANIC 906 详解）

日志（原版 0.3.5 Android 包）：

```
mmap returned read-only address: 0xb400006d7ccfa040
PANIC 906            (PANIC_INTERNAL_ERROR)
TARGET RESET / PANIC 841
FINAL-FRAME-HASH 43eca092…  (独立帧 1)     ← 画面一帧都没推进
```

根因是 **pxt 64 位 NaN-boxing 与 Android 的堆地址布局冲突**：

- `pxtbase.h`：`isDouble(v) = ((uintptr_t)v >> 48) != 0`，即"高 16 位非 0 = 数字"；
  指针必须落在 `< 2^48` 且高 16 位为 0 的区域。
- Linux/Windows 的 malloc 给 `0x7f…`/`0x55…`（高 16 位 0）→ 正常。
- **Android bionic 的 malloc 给 `0xb400_xxxx_xxxx_xxxx`（高 16 位 = 0xb400）** →
  所有堆指针都被判成 double，`gcAllocBlock` 末尾的 `isReadOnly()` 直接 panic。

实测（临时探针程序，未入库）：`malloc` → `0xb400…` 高 16 位非 0；
`mmap(hint=0x200000000)` → 精确命中，高 16 位为 0。所以低地址分配在 Android 上是可行的。

## 试过的修复与为什么还不够

| 改动 | 结果 |
|---|---|
| `Android.mk` 加 `-DPXT_VM` | 无变化。注意：`PXT_VM` 缺失本身就是构建错误（`pxtbase.h` 靠它选 PXT32/PXT64），但宏加上后产物 md5 未变（`4c132959…`），说明这不是当前的瓶颈 |
| `gcAllocBlock` 的 64 位分支改成 mmap 到 `GC_BASE`（`0x2000000000`） | PANIC 906 消失 → 换成 **PANIC 982**（`PANIC_CAST_FROM_NUMBER`），说明 GC 堆之外还有高地址对象 |
| 再加"xmalloc/operator new 全部走低地址 arena + xfree 空转" | 仍然 PANIC 982，`dataEnd=0xb400…`：**VM 内部又拷贝了一份镜像**（`vm_start_from_image` 里），加上 `Pointer tag for 0x400024710 was truncated` 说明还有 32 位截断假设；随后 bionic 在某个非 arena 指针上 `free()` → Aborted |

结论：这不是"补一个宏"能解决的事，需要一次系统性移植——把 **pxt 的全部堆（GC 堆、
fiber、对象、字符串）以及核心侧持有的镜像 buffer** 都放到 `< 2^48` 的低地址，并逐处
排查 32 位指针假设。改动面覆盖 `runtime/pxtapp` 多个文件，属于新项目级工作量，
必须逐卡带回归验证。

上述三个实验性改动**已全部回退**，工作树与 0.3.5 发布版本一致；只保留
`tools/mca_host_android.c` 这个测试宿主。

## 前端验证的障碍（无 root 时的装核路径）

RA 的核心目录是 `/data/user/0/com.retroarch.aarch64/cores/`（app 私有），
`/sdcard/RetroArch/cores` 是空的。设备无 root，写不进去，也无法 `run-as`
（production build）。可行路径只有：

1. 用户在 RA 里 **Main Menu → Online Updater → Install or Restore a Core**，
   选本地目录里的 `.so` 装进私有目录（`.info` 另放进「设置 → 目录 → 核心信息」指向的目录）；
2. 或把设备 root 掉，之后核心目录可以直接 `adb push`。

坑点（实测）：
- `.info` 的**主文件名必须与 `.so` 的相同**（`xxx_libretro.so` ↔ `xxx_libretro.info`），
  否则列表里没有描述；
- 换 `.info` 后要删掉同目录的 `core_info.cache`，RA 否则继续用旧缓存；
- 核心信息目录里**不要**顺手放 `.so`，RA 只扫 `.info`，放了容易让人以为"已经安装"。

## 如果以后要在自建 APK 里加载本核心

**RetroArch 场景不需要做任何事**（已真机验证）。只有"自己的 app（`targetSdkVersion >= 30`）
内嵌本核心"时才需要下面的移植，建议顺序：
1. 先写一个"低地址分配器"（size-class + free list，替换 xmalloc/xfree 与 operator new），
   在 arm64 chroot 之外用 Android 真机跑 `mca_host` 验证 21 卡带哈希；
2. `retro_load_game` 里把前端给的 `game->data` 拷进低地址 buffer 再交 VM；
3. 逐处清理 `(uint32_t)ptr` 类截断与 `Pointer tag … truncated` 告警；
4. 通过后把 `mca_host` 的 21 卡回归加入 CI/工具机脚本。

## 常规长测机（Mi Max 2，2026-11-08 14:30 落地）

选它的理由只有一条：**SDK 25 < 30，bionic 不打堆 tag**，所以 shell 宿主的哈希与桌面逐位
可比，不需要 APK、不需要点屏幕、不需要 root。

```bash
# 21 张卡带 × 600 帧，与桌面 x86_64 基线逐张比对（约 30 秒一轮）
bash tools/android_test/run_shellhost.sh --carts out/android_test/carts21
# 基线默认用 tools/fixtures/android21-baseline.txt（21 张卡带 × 600 帧，已入库）

# 长测：连跑 10 轮，任何一轮哈希漂移或非 0 退出都会让脚本返回 1
bash tools/android_test/run_shellhost.sh --rounds 10 --no-push

# 单张卡带 5 分钟游戏时间（18000 帧），用来查长跑漂移/内存
bash tools/android_test/run_shellhost.sh --only arcade-jumpy-platformer.pxt64 --frames 18000 --no-push
```

实测结果：

| 项目 | 结果 |
|---|---|
| 21 张卡带 × 600 帧 | **21/21 与桌面基线逐位一致**，`rc=0`，单张 0–3 s |
| 连跑 3 轮（63 次）+ 10 轮（210 次）+ 5 轮（105 次） | 全部一致，`rc` 全 0，无崩溃、无超时 |
